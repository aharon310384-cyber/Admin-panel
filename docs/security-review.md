# Обзор безопасности Postmanfox

> Дата: 2026-06-21. Контекст: деплой на сервер многоагентной системы
> (`72.56.109.22`, Timeweb, Ubuntu 24.04), домен `cabinet.postmanfox.com` + HTTPS.
> Это обсуждение/аудит, без внесения изменений. Часть пунктов подтверждена по ходу
> деплоя, часть требует дополнительной проверки (помечено).

## Короткий вердикт

Для **теста и мягкого старта на узком круге** — приемлемо. Для **массового приёма
реальных клиентов с их персональными данными** — пока **не закалено**, есть несколько
конкретных дыр. Оценка: «работает и зашифровано снаружи, но периметр сервера дырявый».

## Что сделано хорошо ✅

- **HTTPS** с валидным сертификатом Let's Encrypt, http→https редирект.
- Пароли клиентов — **bcrypt** (не хранятся в открытом виде).
- Сессия кабинета — **подписанная** (HMAC), cookie `httpOnly` + `Secure` + `SameSite=lax`
  (браузерный скрипт её не украдёт; флаг Secure теперь активен на HTTPS).
- Telegram: проверка подписи `initData` и **секрет webhook**
  (чужой не подделает запросы боту).
- Секреты (токен бота, ключи) — в `.env` (chmod 600) и **не** уходят в GitHub
  (`assets/` и `scripts/server/` добавлены в `.gitignore`).

## Уязвимые места ⚠️ (по приоритету)

### 🔴 Высокий приоритет

1. **Файрвол выключен** (`ufw` неактивен — подтверждено). Все порты открыты в интернет напрямую.
2. **Приложение торчит наружу по «голому» IP без HTTPS** — `http://72.56.109.22:45371`
   отвечает в обход nginx и шифрования (подтверждено). Замочек можно обойти, зайдя по IP —
   тогда логин/пароль и cookie летят **незашифрованными**. Сводит на нет часть пользы от HTTPS.
   Причина: приложение слушает `0.0.0.0:45371`, а не только `127.0.0.1`.
3. **Соседство с многоагентной системой, обе — под root.** Если ломают одну, под угрозой
   весь сервер: и база клиентов, и ключи многоагентной (OpenRouter, мосты Telegram/WeChat).
   Общий «радиус поражения».
4. **Слабый пароль админа.** По заметкам был `admin@shop.ru / admin123`. Если ещё активен —
   серьёзно (полный доступ к данным). **Требует проверки.**
5. **Тестовый клиент `ABC` с известным паролем** `fox-test-2026` — в системе с реальными
   данными. Пароль засветился в рабочем чате.

### 🟡 Средний приоритет

6. **Нет защиты от перебора** на входах (код+пароль клиента, админка). Коды клиентов короткие
   (`AA`, `ABC`) и угадываемые — можно подбирать. Нужен лимит попыток (rate limiting / lockout).
7. **Всё работает под root** — компрометация Node-приложения = root на сервере.
8. **База SQLite с телефонами клиентов** лежит файлом, без шифрования at-rest. Бэкапы — на том
   же сервере (нет offsite). Вопрос 152-ФЗ (персональные данные).
9. **SSH-ключ без пароля** на рабочем компьютере + **токен бота светился в чате** — у кого
   доступ к ним, тот имеет доступ к серверу/боту.

### 🟢 Надо проверить (без просмотра не утверждаю)

10. Проверяется ли «свежесть» `auth_date` у Telegram `initData` (защита от replay старого входа).
11. SSH: отключён ли вход по паролю для root, стоит ли `fail2ban`, включены ли
    авто-обновления безопасности (`unattended-upgrades`).

## Главная мысль

Снаружи (шифрование, пароли, подписи) — сделано грамотно. Слабое звено — **периметр сервера**:
выключенный файрвол, открытый по IP порт, root, соседство с другой системой. Это не «дыра в
коде», а **закалка инфраструктуры** — чинится без переписывания, набором настроек.

## Статус закалки на 2026-06-21 (что уже сделано)

- ✅ **#1 Файрвол** — `ufw` включён. Открыты только 22/80/443/8443/10050, остальное закрыто.
- ✅ **#2 Доступ по IP** — приложение перепривязано на `127.0.0.1:45371` (флаг `-H`),
  снаружи по IP недоступно, только через nginx/HTTPS. Проверено.
- ⏳ **#3 Соседство под root** — требует отдельного сервера (инфраструктурное решение).
- ✅ **#4 Пароль админа** — слабый `admin123` заменён на стойкий. Подтверждено, что слабый
  больше не подходит. (Демо-email `admin@shop.ru` можно сменить на реальный.)
- ✅ **#5 Тестовый пароль клиента ABC** — заменён на новый стойкий (старый `fox-test-2026` недействителен).
- ✅ **#6 Rate limiting на входах** — добавлен в nginx (`limit_req` zone `pmf_login`,
  10r/m, burst 10) на `/api/cabinet/password-login` и `/api/auth/callback/credentials`.
  Проверено: после ~10 попыток с IP → 429; обычные страницы не затронуты.
- ⏳ **#7 Запуск под non-root** — не сделано (трудоёмко, делать аккуратно).
- ◐ **#8 Бэкапы** — настроен автоматический ЛОКАЛЬНЫЙ бэкап БД (cron, ежедневно 03:30,
  14 копий, `sqlite3 .backup`). Offsite (вне сервера) — ещё нужно решение по хранилищу.
- ⏳ **#9 Passphrase на SSH-ключ / перевыпуск токена бота** — на стороне пользователя.
- ✅ **#10 Свежесть Telegram `initData`** — проверено: подпись + `auth_date` (окно 24ч). В порядке.
- ✅ **#11 SSH** — проверено: вход по паролю отключён, root только по ключу,
  `unattended-upgrades` включён. `fail2ban` нет (малокритично при отключённом пароле).

## Возможные шаги по закалке (на будущее, не выполнялись)

- Включить `ufw`: разрешить только 22/80/443, закрыть прямой доступ к 45371/38731/5555.
- Привязать приложение к `127.0.0.1:45371` (наружу — только через nginx/HTTPS).
- Сменить пароль админа на стойкий; убрать тестовый пароль клиента `ABC`.
- Добавить rate limiting / блокировку после N неудачных попыток входа.
- Запускать приложение под отдельным непривилегированным пользователем (не root).
- Для реального запуска — вынести на отдельный сервер от многоагентной системы.
- Offsite-бэкапы БД (например, в объектное хранилище), проверка восстановления.
- SSH: запретить парольный вход root, поставить `fail2ban`, включить авто-обновления.
- Поставить пароль (passphrase) на SSH-ключ; перевыпустить токен бота (он светился в чате).
- Проверить/добавить проверку `auth_date` в валидации Telegram `initData`.
