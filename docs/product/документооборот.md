# Документооборот PostmanFox (модель v2)

Обновлено: 2026-10-16
Статус: таблицы всех документов созданы, нумерация и разделение «задача / посылка» работают. АРМы, которые создают документы этапов и переключают статусы, — следующий этап.

Документ для разработчиков и агентов: цепочка документов, решения владельца, таблицы, нумерация, обновление рабочей базы. Перед изменениями заказов, посылок, складских и денежных документов читать его.

## 1. Цепочка документов

```
Заказ (строка-товар)                     Order               ZK-000001
├─ Сортировка          ┐ документы       Sorting             SR-000001
├─ Приём заказа        │ по коробке      Receiving           PR-000001
│   └─ Раскладка       ┘ (вход. трек)    Placement           RS-000001
├─ Задача на формирование посылки        ParcelTask          SM3956US (формат Excel)
│   ├─ В работе                          статус IN_PROGRESS
│   ├─ Сборка                            Assembly            SB-000001
│   ├─ Упаковка                          Packing             UP-000001
│   ├─ Взвешивание                       Weighing            VZ-000001
│   └─ Посылка                           Parcel              PS-000001
│       ├─ Комплектация коробов          Box                 KR-000001
│       ├─ Реестр отправки               Manifest            RO-000001
│       │   └─ Документы AWB             Awb                 AW-000001
│       │       ├─ Счёт на оплату услуг          AgentInvoice  SA-000001
│       │       │   └─ Заявка на выплату агенту  AgentPayout   VA-000001
│       │       └─ (счетов сколько угодно, у каждого свой агент)
│       ├─ Заявка на пополнение баланса клиента  TopUpRequest  PB-000001
│       │   └─ Приход ДС                         Payment       PD-000001
│       │       └─ Распределение оплат по посылкам PaymentAllocation RP-000001
│       └─ Изменение долга клиента               ClientLedger  DK-000001
```

Справочники: `StorageCell` (ячейки хранения), `Agent` (агенты / подрядчики). Счётчики номеров: `DocumentCounter`.

## 2. Решения владельца (2026-10-16)

1. **Заказ = товар** (1 товар + 1 входящий трек-номер), как в модели v2. Документы по коробке — сортировка, приём, раскладка — привязаны к входящему трек-номеру и охватывают все заказы-строки из коробки (`Order.sortingId`, `Order.receivingId`).
2. **Задача и посылка разделены.** Номер формата Excel (`SM3956US`: код клиента + сквозной номер + страна) — у задачи. Посылка — документ `PS-000001`. Клиент в кабинете и в Telegram видит номер задачи: его он знает и указывает в комментарии к оплате.
3. **Сборка, упаковка, взвешивание, приём** — пока только таблицы документов. Автоматика (документ ставит статус, пишет вес) — вместе с АРМами.
4. **Оплата:** посылка отмечается оплаченной автоматически, когда распределённые на неё оплаты покрывают итог (`lib/parcel-payment.ts`). Ручная галочка администратора остаётся.
5. **Приписки к номеру из Excel** (`01 DHL`, `Sea`) — в примечании задачи.
6. **Потеряшки (`LostItem`) не трогаем** — связь с сортировкой «клиент не опознан» сделаем отдельно.
7. **Трек-номера:** у заказа — «Входящий трек-номер» (`Order.trackNumber`, китайская служба: SF, J&T…), у посылки — «Трек-номер посылки» (`Parcel.trackingNumber`, международный). Оба не путать с номером документа.

## 3. Как сейчас идёт процесс

- Заказ создаётся (форма / массовый ввод) — получает `ZK-…`.
- «Оформить на отправку» из принятых заказов (`createParcelFromOrders`) в **одной транзакции** создаёт задачу (`SM…`, статус NEW) и посылку (`PS-…`, статус FORMED), связывает заказы с обеими (`Order.parcelTaskId`, `Order.parcelId`), пишет историю статусов и услуги посылки. Если что-то не записалось — не создаётся ничего.
- Пока АРМов нет, задача и посылка создаются одновременно. Когда появятся АРМы, посылка будет создаваться после взвешивания, а задача — проходить статусы IN_PROGRESS → ASSEMBLED → PACKED → WEIGHED → COMPLETED.
- Дальше всё как раньше: статусы посылки, квитанция, оплата, трек.

## 4. Таблицы и поля

Общие поля документов: `number` (уникальный), `note`, `createdById` → `User`, `createdAt`, `updatedAt`, `deletedAt`.

| Таблица | Свои поля | Связи |
|---|---|---|
| `Sorting` | `trackNumber`, `customerId?`, `clientIdentified` | заказы — `Order.sortingId` |
| `Receiving` | `trackNumber`, `placesCount`, `weightKg`, `condition` (INTACT / DAMAGED), `photoUrl` | заказы — `Order.receivingId`; 1:1 раскладка |
| `Placement` | — | `receivingId` @unique, `cellId` → `StorageCell` |
| `ParcelTask` | `status` (ParcelTaskStatus), `customerId`, `destinationCountry` | заказы — `Order.parcelTaskId`; 1:1 сборка, упаковка, взвешивание, посылка (`Parcel.parcelTaskId` @unique) |
| `Assembly` + `AssemblyItem` | `allFound`; строки: заказ + `found` | `parcelTaskId` @unique |
| `Packing` | `packagingType`, `placesCount` | `parcelTaskId` @unique |
| `Weighing` | `weightKg`, `lengthCm`, `widthCm`, `heightCm`, `volumetricWeightKg` | `parcelTaskId` @unique |
| `Box` | `weightKg` | `manifestId?`; посылки — `Parcel.boxId` |
| `Manifest` | `shipDate`, `destinationCountry` | коробы, AWB |
| `Awb` | `awbNumber` (у перевозчика), `carrier`, `flightNumber`, `departureDate` | `manifestId` |
| `AgentInvoice` | `externalNumber`, `invoiceDate`, `amount`, `currency` | `agentId`, `awbId` |
| `AgentPayout` | `amount`, `currency`, `status`, `paidAt` | `agentInvoiceId` (несколько = частичная оплата) |
| `TopUpRequest` | `amount`, `currency`, `status` | `customerId` |
| `Payment` | `amount`, `currency`, `method`, `receivedAt` | `customerId`, `topUpRequestId?` |
| `PaymentAllocation` + `PaymentAllocationItem` | строки: посылка + сумма (в валюте прихода) | `paymentId` |
| `ClientLedger` | `amount` со знаком (+ долг вырос, − уменьшился), `currency`, `reason` | `customerId`, `parcelId?`, `paymentAllocationId?`. Долг = сумма строк |

Новые поля существующих таблиц (все необязательные, чтобы `db push` прошёл на рабочей базе): `Order.number` (@unique), `Order.sortingId`, `Order.receivingId`, `Order.parcelTaskId`, `Parcel.parcelTaskId` (@unique), `Parcel.boxId`. `Parcel.number` теперь `PS-…`.

## 5. Нумерация

- `lib/document-numbers.ts` — префиксы и `nextDocumentNumber(db, type)`: атомарный счётчик в `DocumentCounter`, формат `ПРЕФИКС-000001`. Вызывать в транзакции создания документа.
- `lib/parcel-number.ts` — номер задачи `nextParcelTaskNumber(code, country)`: сквозной номер = максимум по всем номерам задач (+ ещё не перенесённым номерам посылок) + 1. `splitLegacyTaskNumber` разбирает номер Excel на номер, страну и приписку. `clientParcelNumber` — что показывать клиенту (номер задачи, иначе номер посылки).

## 7. Обновление рабочей базы (один раз)

```bash
# перед этим — резервная копия data/postmanfox.db
npm run db:push                      # новые таблицы и поля; на базе с данными проходит без предупреждений
npm run db:upgrade:document-flow     # номера заказам, задачи из старых номеров посылок, посылкам — PS-…
```

`prisma/upgrade-document-flow.ts`, одна транзакция, повторный запуск ничего не меняет:
1. Заказам без номера — `ZK-…` в порядке создания.
2. Каждой посылке без задачи — задача: прежний номер посылки → номер задачи (приписка `01 DHL` / суффикс `_2` → примечание «Номер в Excel: …»; совпадения получают `_2`, `_3`), страна — из получателя или номера, статус — по статусу посылки (FORMED → NEW, ASSEMBLED, PACKED, READY_TO_SHIP / SHIPPED / DELIVERED → COMPLETED, RETURNED / UTILIZED → CANCELED), автор — первый администратор. Посылке — `PS-…` в порядке создания.

Проверено на копии базы v2 с номерами `AT1536DE 01 DHL`, `AT1536DE 02 DHL`, `GG1542UA Sea`, `SM3956US`, `OS4057PL_2`, `PF000123`; следующая задача после них получает сквозной номер 4058.

## 10. К обсуждению с владельцем

### Атомарность оформления посылки и услуга «Оставить оригинальную упаковку»
Записано 2026-10-16, владелец попросил обсудить отдельно.

- **Что нашлось.** На тестовой базе оформление посылки падало: в справочнике `ServiceTariff` не было услуги `KEEP_ORIGINAL_PACK`. Её добавляет отдельный скрипт `scripts/add-keep-original-pack.js`, в `prisma/seed-v2.js` её нет. Значит, на любой новой базе без этого скрипта оформление ломается.
- **Слабое место.** В исходной model-v2 посылка создавалась, потом записывались услуги, потом заказы связывались с посылкой. При сбое на услугах оставалась посылка без заказов и без услуг.
- **Что сейчас в PR #2.** Задача, посылка, связи заказов, история статусов **и услуги** записываются в одной транзакции (`createParcelFromOrders`, `saveParcelServices(..., tx)`). При сбое не создаётся ничего, заказ остаётся принятым. Это изменение существующего поведения, сделано без обсуждения.
- **Варианты для решения:**
  1. Оставить как в PR #2 — оформление целиком или никак.
  2. Вернуть порядок model-v2: услуги после транзакции.
  3. Дополнительно (не исключает 1 или 2): добавить `KEEP_ORIGINAL_PACK` в `seed-v2.js` и / или не падать на неизвестной услуге, а пропускать её с предупреждением.
