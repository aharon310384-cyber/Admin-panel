# Целевая схема БД Postmanfox — ЧЕРНОВИК v1
Дата: 2026-06-19. На основе опросников 2.0–2.5. ЭТО ПРОЕКТ для согласования (к БД не применяется).

## 1. Карта сущностей (связи)

```
USER (сотрудники: ADMIN / MANAGER / [WAREHOUSE потом])

CUSTOMER (клиент) ──1:*── RECIPIENT (получатель)
   │                          │
   │ 1:*                      │ 1:*
   ▼                          ▼
ORDER (заказ = строка = товар: 1 товар + 1 трек)
   │  status: NEW → IN_QUEUE → RECEIVED → FORMED ...
   │  *:1 (nullable, пока не оформлен)
   ▼
PARCEL (посылка = документ сборки, номер при оформлении)
   │  status: FORMED → ASSEMBLED → PACKED → READY → SHIPPED → DELIVERED
   ├──1:*── PARCEL_SERVICE (применённые услуги = строки квитанции)
   ├──1:*── PARCEL_STATUS_HISTORY
   └── итог: расчёт в $ и ¥

Справочники:
  SHIPPING_TARIFF (тарифы доставки: страна+вид → ставка $/кг, оформление, дни, оплата до/после)
  SERVICE_TARIFF  (услуги: консолидация 0.3$/кг, проверка 1$/кг, и т.д.)
  PRODUCT_NAME    (наименования + категория + HS-код)  [HS — отдельная сессия]
  COUNTRY         (страны + [лимиты потом])
  FINANCE_SETTINGS (курс CNY/USD)

Регистры:
  LOCAL_DELIVERY  (доставка до склада: ¥/$/трек Китая/автор/дата → одной строкой в расчёт)
  LOST_ITEM       (потеряшки) [детально потом]
```

## 2. Сущности и поля

### USER (есть)
`id, email, password, name, role(ADMIN|MANAGER), createdAt…`  → потом роль WAREHOUSE.

### CUSTOMER (клиент — есть, дополняем)
`id, code(уникальный), фио(last/first/middle), name, phone, email, country, city, address,
 telegram*(userId/chatId/username/linkedAt), passwordHash, createdAt, updatedAt, deletedAt`
Связи: recipients[], orders[], parcels[].

### RECIPIENT (получатель — НОВАЯ)
`id, customerId→Customer, name, phone, countryCode→Country, city, address, postalCode,
 createdAt, updatedAt, deletedAt`
Один клиент → много получателей. Клиент видит своих; менеджер — всех.

### ORDER (заказ = строка = товар — переосмысление текущего OrderTrackItem/Order)
```
id
customerId   → Customer (владелец/плательщик)
recipientId  → Recipient (куда везём)
deliveryType (вид доставки: авто/авиа/море/EMS)
-- товар --
productNameId → ProductName (наименование из справочника)
category, hsCode            (декларация; категория из справочника)
declaredValueUsd            (объявленная стоимость = unitPrice × quantity)
trackNumber                 (китайский трек, НЕ уникален)
quantity
unitPriceCny / unitPriceUsd
-- вес (на строке, Z5) --
actualWeightKg, volumetricWeightKg
-- проверка --
detailedCheckRequested (bool)  ← «Детальная проверка и фотоотчёт» (выбирает клиент или менеджер)
productUrl, imageUrl
-- процесс --
status (OrderStatus)
parcelId → Parcel (nullable, заполняется при оформлении)
createdAt, updatedAt, deletedAt
```

### PARCEL (посылка — переосмысление текущего Parcel)
```
id
number            (генерируется при оформлении на отправку)
customerId → Customer
recipientId → Recipient
deliveryType
status (ParcelStatus)
-- веса --
actualWeightKg, volumetricWeightKg
billableWeightKg  (расчётный = фактический по умолчанию, менеджер может перебить вручную)
-- расчёт --
exchangeRateCnyPerUsd  (зафиксирован при оплате, берётся из FinanceSettings)
shippingCostUsd        (Отправка = billableWeightKg × ставка тарифа)
discountPercent        (скидка % от итога, вручную)
totalUsd, totalCny     (итог квитанции)
-- оплата --
isPaid (bool), paidAt
paymentTiming (BEFORE | FLEXIBLE)  ← из тарифа направления
-- отслеживание --
trackingNumber  (трек посылки для клиента)
createdAt, updatedAt, deletedAt
```
Связи: orders[] (строки), services[] (применённые услуги), statusHistory[].

### PARCEL_SERVICE (применённые услуги = строки квитанции — НОВАЯ)
```
id, parcelId → Parcel
serviceCode → ServiceTariff
name (снимок названия)
baseValue   (вес/кол-во/стоимость, от чего считали)
priceUsd, priceCny
```
Пример строк квитанции: Консолидация, Компактная упаковка, Проверка, Страховка, Доставка до склада, Скидка.

### SHIPPING_TARIFF (справочник тарифов доставки — НОВАЯ, выносим из кода)
```
id
direction (страна/направление)         напр. Россия, Украина, Казахстан, EMS-группа…
deliveryType (AUTO|AIR|SEA|EMS)
pricePerKgUsd      (ставка $/кг)
handlingFeeUsd     (оформление $)
minDays, maxDays
paymentTiming (BEFORE | FLEXIBLE)       РФ/EMS/КЗ/БР=BEFORE; Узб/Укр/Молд=FLEXIBLE
volumetricDivisor  (nullable — отложено)
minWeightKg        (nullable — отложено)
active (bool)
```

### SERVICE_TARIFF (справочник услуг — НОВАЯ)
```
code, name
pricingType (PER_KG | PER_ORDER | PERCENT | MANUAL)
value        (0.3 / 0.5 / 1.0 / 2.0 ; для PERCENT — min/max 2–10)
appliesLevel (PARCEL | ORDER)
selectableByClient (bool)   ← true только у «Детальная проверка и фотоотчёт»
```
Данные (с сайта):
| Услуга | pricingType | value | уровень |
|---|---|---|---|
| Консолидация | PER_KG | 0.3 | посылка |
| Компактная упаковка | PER_KG | 0.5 | посылка |
| Стандартная проверка | PER_KG | 1.0 | посылка |
| Детальная проверка и фотоотчёт | PER_ORDER | 2.0 | строка-заказ |
| Доп. страховка | PERCENT | 2–10 (вручную) | от стоимости товаров |
| Усиленная упаковка | MANUAL | по факту | посылка |
| Доставка до склада | MANUAL | по факту (из регистра) | посылка |

### LOCAL_DELIVERY (регистр «Доставка до склада» — НОВАЯ)
```
id
orderId → Order (привязка по треку Китая)
customerId → Customer
parcelNumber (номер посылки)
trackNumberChina
amountCny, amountUsd (по курсу), exchangeRate
authorId → User, createdAt, note
```
Несколько записей → их ОБЩАЯ сумма попадает ОДНОЙ строкой услуги «Доставка до склада» в расчёт посылки.

### Справочники без изменений / лёгкие правки
- COUNTRY (есть) → потом таможенные лимиты.
- PRODUCT_NAME (есть): + category, + hsCode (отдельная сессия).
- FINANCE_SETTINGS (есть): курс CNY/USD.
- LOST_ITEM (потеряшка) — заложим позже.

## 3. Статусы (enums)

### OrderStatus (заказ-строка — до оформления в посылку)
`NEW (Новый) → IN_RECEIVING_QUEUE (В очереди на приём) → RECEIVED (Принят на склад) → FORMED (Оформлен в посылку)`
Ветки: `RECEIVED_WITH_DISCREPANCY (Принят с несоответствием)` (из IN_RECEIVING_QUEUE → далее RECEIVED/RETURNED/UTILIZED), `RETURNED (Возвращён)`, `UTILIZED (Утилизировано)`.

### ParcelStatus (посылка — после оформления)
`FORMED (Оформлена на отправку) → ASSEMBLED (Собран) → PACKED (Упакован) → READY_TO_SHIP (Готова к отправке: формируется квитанция) → SHIPPED (Отправлена) → DELIVERED (Доставлена)`
Ветки: `RETURNED`, `UTILIZED` (в т.ч. из READY_TO_SHIP).
Расформировать посылку можно только пока FORMED (до ASSEMBLED).

## 4. Логика расчёта посылки (= квитанция OS4057PL)
```
Отправка        = billableWeightKg × pricePerKgUsd (тариф направления)
+ оформление    = handlingFeeUsd (тариф)
+ Консолидация  = billableWeightKg × 0.3   (если применена)
+ Компактная упаковка    = billableWeightKg × 0.5
+ Стандартная проверка = billableWeightKg × 1.0
+ Детальная проверка   = (кол-во заказов-строк с флагом) × 2.0
+ Усиленная упаковка   = по факту
+ Доставка до склада   = Σ из регистра LOCAL_DELIVERY (одной строкой)
+ Страховка     = Σ declaredValueUsd × (2–10 % вручную)
− Скидка        = % от промежуточного итога
= ИТОГО $   →   ИТОГО ¥ (× exchangeRate)
```
Оплата: блокирует переход в SHIPPED для тарифов paymentTiming=BEFORE (пока isPaid=false). Для FLEXIBLE — можно отправить без оплаты.

## 5. Что меняется относительно текущей схемы
- Текущий `Order`(таблица Product) = каталог товаров → **становится ORDER (заказ-строка)**; текущий `OrderTrackItem` вливается в ORDER (трек на строке).
- Текущий `Parcel`(таблица Order) → остаётся PARCEL, но чистим/добавляем поля (billableWeight, paymentTiming, discountPercent, services).
- Текущие `ParcelItem` → не нужны (позиция = ORDER напрямую через parcelId).
- НОВЫЕ: Recipient, ParcelService, ShippingTariff, ServiceTariff, LocalDelivery.
- Маппинг имён таблиц приведём в порядок при рефакторинге.

## 6. Согласованные решения (по 4 точкам)
1. ✅ Получатель + deliveryType хранятся на ЗАКАЗЕ; при оформлении ПЕРЕНОСЯТСЯ (копируются) в посылку. Все заказы одной посылки = один получатель + доставка.
2. ✅ Статусы делим: OrderStatus (до посылки) + ParcelStatus (после). НО сквозные общие статусы — `UTILIZED (Утилизировано)`, `RETURNED (Возвращён)` — присутствуют в ОБОИХ наборах (можно утилизировать/вернуть и заказ, и посылку).
3. ⏳ Номер: у ПОСЫЛКИ — number (генерируется при оформлении); у заказа-строки — внутренний id. Нужен ли отдельный номер заказа — решим наглядно на UI (отложено).
4. ✅ «Оформлен на отправку» = статус заказа FORMED + одновременно создаётся PARCEL (FORMED). Связка подтверждена.
