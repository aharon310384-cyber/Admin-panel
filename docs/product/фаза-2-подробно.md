# ФАЗА 2 — после релиза. Подробно по пунктам
Дата: 2026-06-20. Срок каждого — ПРИМЕРНЫЙ (рабочие дни). Внутри указаны: суть, что делаем (БД/бэкенд/UI), зависимости, приоритет.

═══════════════════════════════════════════════════════════════
П1. ПОТЕРЯШКИ (регистр + АРМ)   |  ~2–3 дня  |  приоритет: высокий
═══════════════════════════════════════════════════════════════
Суть: на склад пришёл трек, которого нет в системе (не привязан к заказу). Фиксируем как «потеряшку», потом разбираемся.
БД: новая таблица LostItem — trackNumber, weightKg, customerId(если угадали), parcelNumber, note, photoUrl, authorId, createdAt, status (Потеряшка → Передано на приём / Утилизировано).
Бэкенд: создание из АРМ приёмки («оформить как потеряшку»), смена статуса, привязка к заказу при опознании.
UI: новый раздел «Потеряшки» в админке (список + фильтры по статусу) + кнопка в АРМ приёмки.
Зависимости: после АРМ приёмки (Этап 4 Фазы 1).

═══════════════════════════════════════════════════════════════
П2. ВЫКУПЫ ИЗ МАРКЕТПЛЕЙСОВ / WECHAT (оплата ЗА ТОВАР)   |  ~5–7 дней  |  приоритет: средний
═══════════════════════════════════════════════════════════════
Суть: сейчас оплата только за доставку. Модуль выкупа = система/менеджер покупает товар у поставщика за клиента (китайская цена). Оживают строки квитанции «Закупка» и связанные платежи.
БД: модуль «Выкуп» — таблица Purchase (orderId, поставщик, ссылка, ценаCny, статус выкупа, платёж), оплата за товар отдельно от доставки.
Бэкенд: цикл выкупа (заявка → выкуп → оплата поставщику → приёмка), баланс/платежи клиента за товар.
UI: раздел «Выкупы», привязка к заказу-строке, отдельный платёж.
Зависимости: ядро заказов (Фаза 1). Связан с WeChat-интеграцией для заявок.

═══════════════════════════════════════════════════════════════
П3. HS-КОДЫ И КАТЕГОРИИ НАИМЕНОВАНИЙ   |  ~2–3 дня  |  приоритет: высокий (ты отметил)
═══════════════════════════════════════════════════════════════
Суть: справочник наименований по секциям (Одежда, Обувь, Сумки…) с HS-кодами (ТН ВЭД) для декларации/таможни.
БД: расширить ProductName — category(секция), hsCode, nameRu/En/Cn (есть).
Данные: агент соберёт образец HS-кодов из европейских источников ТН ВЭД по твоим категориям. Ты дашь каркас (/product-names).
UI: справочник по секциям, выбор наименования при создании заказа подтягивает HS.
Зависимости: твой каркас категорий (отдельная сессия).

═══════════════════════════════════════════════════════════════
П4. ДЕЛИТЕЛЬ ОБЪЁМНОГО ВЕСА   |  ~0.5–1 день  |  приоритет: средний
═══════════════════════════════════════════════════════════════
Суть: объёмный вес = Д×Ш×В(см) / делитель. Делитель зависит от вида доставки (авиа ~5000, курьер ~6000, возможно 168).
БД: поле volumetricDivisor в ShippingTariff.
Бэкенд: расчёт объёмного веса по габаритам → влияет на расчётный (billable) вес.
UI: ввод габаритов в карточке посылки/строки, авторасчёт.
Зависимости: тарифы в БД (Этап 2 Фазы 1). Нужно определить значения делителей по направлениям.

═══════════════════════════════════════════════════════════════
П5. МИНИМАЛЬНЫЙ ВЕС ТАРИФА   |  ~0.5 дня  |  приоритет: низкий
═══════════════════════════════════════════════════════════════
Суть: минимальный оплачиваемый вес посылки (если фактический меньше — считаем по минимуму).
БД: поле minWeightKg в ShippingTariff.
Бэкенд: в расчёте billableWeight = max(фактический/объёмный, minWeightKg).
Зависимости: тарифы в БД.

═══════════════════════════════════════════════════════════════
П6. ТАМОЖЕННЫЕ ЛИМИТЫ ПО СТРАНАМ   |  ~1–2 дня  |  приоритет: средний
═══════════════════════════════════════════════════════════════
Суть: лимит беспошлинного ввоза по стране. При оформлении предупреждать, если объявленная стоимость превышает лимит.
БД: поля limitAmount/limitWeight в Country.
Бэкенд: проверка при оформлении посылки, предупреждение менеджеру/клиенту.
UI: индикатор превышения лимита в карточке посылки.
Зависимости: декларация на строке (Фаза 1).

═══════════════════════════════════════════════════════════════
П7. ПЕРЕИМЕНОВАНИЕ СТАТУСОВ (финальные названия)   |  ~0.5–1 день  |  приоритет: низкий
═══════════════════════════════════════════════════════════════
Суть: финальные пользовательские названия статусов (RU; возможно EN/CN для клиента).
Реализация: словарь названий статусов (i18n), отдельно от кодов enum. Меняем тексты без миграции данных.
Зависимости: процесс устаканится после Фазы 1.

═══════════════════════════════════════════════════════════════
П8. АРХИТЕКТУРА CRM (менеджер) / ERP-WMS (склад)   |  ~3–5 дней  |  приоритет: средний
═══════════════════════════════════════════════════════════════
Суть: разделить рабочие места. CRM — клиенты, заказы, расчёты, оплаты, общение (менеджер). ERP/WMS — приёмка, сборка, упаковка, отправка (склад).
Реализация: разные интерфейсы/дашборды под роли, навигация под задачи роли.
Зависимости: роли склада (П9), наполненные Документы/Приёмка (Фаза 1).

═══════════════════════════════════════════════════════════════
П9. РОЛИ СКЛАДСКИХ РАБОТНИКОВ   |  ~1 день  |  приоритет: средний
═══════════════════════════════════════════════════════════════
Суть: роль WAREHOUSE (склад) с доступом только к АРМ (приёмка/сборка/упаковка), без финансов и клиентов.
БД: добавить WAREHOUSE в enum UserRole.
Бэкенд: проверки прав по роли (middleware/guards).
UI: ограничение разделов по роли.

═══════════════════════════════════════════════════════════════
П10. ВХОД ЧЕРЕЗ WECHAT   |  ~3–5 дней (+ внешний блокер)  |  приоритет: средний
═══════════════════════════════════════════════════════════════
Суть: вход/привязка клиента через WeChat (аналог Telegram). По плану из памяти.
БД: поля Customer.wechatOpenId/UnionId/LinkedAt.
Бэкенд: WeChat Mini Program (wx.login → openid) или OAuth, привязка по телефону (getPhoneNumber).
БЛОКЕР: регистрация WeChat Mini Program/Official Account (бизнес-верификация, китайское юрлицо/агент).
Зависимости: клиентская сессия (готова). Решить вопрос с регистрацией WeChat.

═══════════════════════════════════════════════════════════════
П11. ДОКРУТКА TELEGRAM-ВХОДА   |  ~0.5–1 день  |  приоритет: высокий (быстро)
═══════════════════════════════════════════════════════════════
Суть: довести Telegram Mini App вход до рабочего (код готов).
Реализация: на ПРОД-домене (Timeweb) — setWebhook + Menu Button бота (/entrance) + тест привязки по номеру и автологина.
Зависимости: релиз на Timeweb (постоянный домен). Отдельный прод-бот.

═══════════════════════════════════════════════════════════════
П12. ИНТЕГРАЦИИ С ВНЕШНИМИ СИСТЕМАМИ   |  ~3–10 дней (зависит)  |  приоритет: уточнить
═══════════════════════════════════════════════════════════════
Суть: ты планируешь интеграции. НУЖНО УТОЧНИТЬ С КАКИМИ: 1С? курьерские/трекинг API? маркетплейсы? бухгалтерия? платёжные системы?
Реализация: API-слой (REST/webhook) под каждую интеграцию. Срок зависит от количества и сложности.
Зависимости: стабильное ядро. Список систем от тебя.

═══════════════════════════════════════════════════════════════
П13. «1 ТРЕК = МНОГО КОРОБОК / ДЕЛЕНИЕ»   |  ~2–3 дня  |  приоритет: средний
═══════════════════════════════════════════════════════════════
Суть: при приёмке трек может быть: 1 трек=1 коробка=1 строка; 1 трек=много коробок; 1 трек делится на много строк.
Реализация: в АРМ приёмки — обработка многокоробочных треков, привязка коробок к строкам, частичный приход.
Зависимости: АРМ приёмки (Фаза 1).
