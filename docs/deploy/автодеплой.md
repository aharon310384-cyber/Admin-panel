# Автодеплой через GitHub Actions

Обновление рабочего сервера (Timeweb, `/opt/postmanfox`, PM2-процесс `postmanfox`) по кнопке в GitHub: Actions → **«Сервер»** → Run workflow.

| Команда | Что делает |
|---|---|
| `status` | Только смотрит: какая версия стоит и сколько коммитов в GitHub новее, изменённые файлы, база, бэкапы и ночной бэкап в cron, PM2, автозапуск после перезагрузки, ответ админки, что занимает диск, настроена ли самоочистка журналов, память, нужна ли перезагрузка |
| `deploy` | Выкатывает `refactor/model-v2`: бэкап базы (`backup-db.sh`) → остановка админки → новый код → `npm ci`, если менялись зависимости → `prisma db push` → `npm run db:upgrade` → сборка → запуск → проверка, что админка отвечает 200 |
| `postgres` | Один раз: перевод базы с SQLite на PostgreSQL — см. раздел ниже |
| `cleanup` | Самоочистка журналов, админку не останавливает, повторять можно — см. раздел ниже |

Если на шаге после остановки что-то упало, `deploy` возвращает код к прежней версии, собирает и запускает её. База при этом не откатывается: свежий бэкап лежит в `backups/`. Если на сервере кто-то вручную изменил файлы программы, `deploy` отказывается и ничего не трогает. Если новая версия рассчитана на другую базу, чем стоит на сервере (SQLite / PostgreSQL), `deploy` тоже отказывается.

Админка недоступна около минуты, пока идёт сборка.

## Как устроено

- `.github/workflows/server.yml` — задача GitHub Actions. Подключается к серверу по SSH и передаёт команду.
- `/usr/local/bin/postmanfox-ci` — точка входа на сервере. Ключ GitHub может выполнить **только её**: ограничение `command=…,restrict` в `authorized_keys`. Она получает свежий `scripts/deploy/server.sh` из `origin/refactor/model-v2` и запускает его.
- `scripts/deploy/server.sh` — сами команды `status`, `deploy`, `postgres`. Меняется обычным pull request, на сервер руками ходить не нужно.
- `npm run db:upgrade` — все обновления данных по порядку. Каждое можно запускать повторно. Новое обновление данных добавляется в эту команду.

Журналы задач видны всем, пока репозиторий публичный. Поэтому скрипт не выводит секреты, адреса и данные клиентов.

## Переход на PostgreSQL (команда `postgres`)

Запускается один раз, после того как в `refactor/model-v2` слита версия с `provider = "postgresql"`. Админка недоступна 1–3 минуты.

Сначала проверки, при любой из них ничего не меняется:
- на сервере ещё SQLite, а в GitHub уже версия для PostgreSQL;
- файл SQLite не держит открытым никакая программа, кроме админки (иначе она осталась бы на старой базе);
- `DATABASE_URL` не задан у самого PM2 (демона), а в настройках других программ PM2 нет базы админки — иначе они остались бы на старой базе;
- в PostgreSQL нет базы или пользователя `postmanfox`, созданных не этим скриптом (свои он помечает комментарием `postmanfox-admin`).

Потом, пока админка ещё работает: установка PostgreSQL (`apt`, если его нет), пользователь и база `postmanfox` (UTF-8, `C.UTF-8`) со случайным паролем. Пароль пишется только в `.env`, в журнал не выводится.

Дальше админка останавливается:
1. копия `.env` → `backups/env-before-postgres`, бэкап SQLite;
2. новый код, `DATABASE_URL` в `.env` → PostgreSQL, `prisma db push` — таблицы;
3. `npm run db:copy-from-sqlite` (`prisma/sqlite-to-postgres.ts`) — перенос всех таблиц и сверка каждой строки с SQLite в одной транзакции;
4. `npm run db:upgrade`, сборка, запуск, проверка ответа 200 и того, что админка работает с новой базой.

На рабочем сервере `DATABASE_URL` записан ещё и в настройках PM2 админки, и он важнее `.env`. Поэтому при запуске адрес меняется и там (`pm2 restart --update-env`), а список PM2 сохраняется (`pm2 save`), чтобы после перезагрузки админка поднялась с новой базой. При откате возвращается прежний адрес. **Меняя адрес базы потом, менять его в обоих местах.** `status` показывает, у каких программ PM2 задан `DATABASE_URL` и совпадает ли он с `.env`.

При ошибке на любом из этих шагов `.env` и код возвращаются, админка собирается и запускается на SQLite. Файл SQLite при переходе только читается и остаётся на месте.

Перенос пишет в журнал только количества, названия таблиц и полей. Полный текст ошибки — на сервере в `node_modules/.prisma-sqlite/error.log`.

Проверено на копии сервера (SQLite → PostgreSQL 16):
- успешный переход, в том числе с `DATABASE_URL` в настройках PM2, и запуск после перезагрузки (`pm2 resurrect`);
- откат при ошибке в данных и при сбое после смены адреса в PM2;
- отказ, если файл SQLite держит другая программа или у другой программы в PM2 указана база админки;
- отказ повторного запуска;
- `deploy` и бэкап после перехода, восстановление бэкапа.

### Бэкапы после перехода
`backup-db.sh` смотрит на `DATABASE_URL`: для PostgreSQL делает `backups/postmanfox-ДАТА.dump` (`pg_dump`, формат custom), хранит 14 последних. Прежние `.db` остаются. Восстановление — в пустую базу:
```bash
pg_restore --clean --if-exists --no-owner -d "<DATABASE_URL из .env без ?schema=public>" backups/postmanfox-ДАТА.dump
```

## Самоочистка журналов (команда `cleanup`)

- **Журналы PM2** (админка, `multi-agent`, сам PM2) сами по себе растут без конца. `cleanup` ставит `/etc/logrotate.d/postmanfox-pm2`: раз в сутки или при размере от 20 МБ журнал уходит в сжатую копию, хранятся 14 копий. `copytruncate` — PM2 держит файлы открытыми, поэтому журнал копируется и обнуляется на месте, PM2 пишет дальше без перезапуска. Накопленное сжимается сразу. Запускает `logrotate` таймер systemd `logrotate.timer` (в Ubuntu включён, `cleanup` проверяет).
- **Системный журнал** (journald) — не больше 300 МБ: `/etc/systemd/journald.conf.d/postmanfox.conf`, перезапуск `systemd-journald`, лишнее удаляется сразу.
- **Кэш скачанных пакетов apt** очищается (`apt-get clean`).

До и после команда показывает, что занимает диск: журналы, программа админки, бэкапы, база, `multi-agent`, кэши, файл подкачки, система. То же — в `status`.

## Настройка (один раз)

### 1. Ключ на компьютере (PowerShell)
```powershell
ssh-keygen -t ed25519 -C github-ci-postmanfox -f $HOME\.ssh\github-ci
```
На вопросы про passphrase — дважды **Enter** (без пароля: ключом пользуется GitHub без человека).

### 2. Точка входа на сервере (консоль Timeweb, под root)
Сначала напечатать руками, чтобы вставка работала: `bind 'set enable-bracketed-paste off'`. Затем вставить:
```bash
cat > /usr/local/bin/postmanfox-ci <<'EOF'
#!/bin/bash
set -euo pipefail
cd /opt/postmanfox
git fetch -q origin refactor/model-v2
git show origin/refactor/model-v2:scripts/deploy/server.sh > /root/.postmanfox-server.sh
exec bash /root/.postmanfox-server.sh "${SSH_ORIGINAL_COMMAND:-status}"
EOF
chmod 755 /usr/local/bin/postmanfox-ci && echo "Точка входа установлена"
```
Так точка входа установлена на рабочем сервере (2026-10-16). Если консоль Timeweb сбоит на многострочной вставке, шаги 2 и 3 можно сделать одной строкой: прислать Claude **публичный** ключ (`github-ci.pub`, он не секретный), и он соберёт команду с ключом внутри.

### 3. Публичный ключ на сервер
На компьютере (PowerShell) скопировать публичный ключ:
```powershell
Get-Content $HOME\.ssh\github-ci.pub | Set-Clipboard
```
На сервере вставить команду, а на вопрос `Публичный ключ:` — вставить скопированное:
```bash
read -p "Публичный ключ: " KEY; KEY=${KEY%$'\r'}; case "$KEY" in "ssh-ed25519 "*" github-ci-postmanfox") install -d -m 700 /root/.ssh && touch /root/.ssh/authorized_keys && sed -i '/github-ci-postmanfox/d' /root/.ssh/authorized_keys && echo "command=\"/usr/local/bin/postmanfox-ci\",restrict $KEY" >> /root/.ssh/authorized_keys && chmod 600 /root/.ssh/authorized_keys && echo "Ключ добавлен";; *) echo "Это не публичный ключ github-ci-postmanfox";; esac
```
Проверка точки входа на сервере:
```bash
/usr/local/bin/postmanfox-ci status
```

### 4. Секреты в GitHub
Settings → Secrets and variables → Actions → New repository secret:

| Имя | Значение | Как получить (PowerShell) |
|---|---|---|
| `DEPLOY_HOST` | `64.188.58.224` | — |
| `DEPLOY_USER` | `root` | — |
| `DEPLOY_SSH_KEY` | приватный ключ целиком | `Get-Content $HOME\.ssh\github-ci -Raw \| Set-Clipboard` |

После того как секрет `DEPLOY_SSH_KEY` сохранён, приватный ключ на компьютере больше не нужен: `Remove-Item $HOME\.ssh\github-ci`.

Ключ сервера в секретах не хранится. Задача сама получает его с сервера и сверяет с отпечатком `HOST_FINGERPRINT` в `server.yml`. Если не совпал, задача останавливается и не подключается. Отпечаток меняется только при переустановке сервера: узнать новый — `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` в консоли сервера, затем поправить `server.yml`.

### 5. Основная ветка
Settings → General → Default branch → `refactor/model-v2`. GitHub показывает кнопку запуска задачи только для задач из основной ветки.

## Если репозиторий станет закрытым
Сервер забирает код из GitHub без пароля, пока репозиторий публичный. Перед тем как сделать его закрытым, на сервер нужно добавить deploy key (ключ только для чтения) и переключить `origin` на адрес `git@github.com:…`.
