# Документооборот PostmanFox — техническое описание

Обновлено: 2026-10-16
Статус: структура таблиц и нумерация готовы, данные из Excel переносятся. Экранов для новых документов (кроме посылок) пока нет.

Документ для разработчиков и агентов: что создано, как связано, где лежит код и какие решения приняты. Инструкция для владельца простым языком — `docs/instruktsiya-dokumentooborot.docx`.

---

## 1. Контекст

PostmanFox — доставка посылок из Китая (склад в Гуанчжоу). Раньше учёт вёлся в Excel: одна строка листа `ALL 6` = одна отправка с номером вида `AT1536DE`. Админка начиналась как шаблон интернет-магазина, поэтому строки Excel импортировались в модель `Order` («Заказ»).

Владелец описал полную цепочку документов — от поступления коробки на склад до расчётов с клиентом и подрядчиками. Выяснилось, что строка Excel — это посылка (и задача на её формирование), а не заказ. Отсюда переименование `Order` → `Parcel` и новая модель `Order` для входящих коробок.

## 2. Цепочка документов

Каждый документ — отдельная таблица в одной базе (SQLite, `prisma/schema.prisma`).

```
Заказ                                   Order               ZK-000001
├─ Сортировка                           Sorting             SR-000001
├─ Приём заказа                         Receiving           PR-000001
│   └─ Раскладка                        Placement           RS-000001
├─ Задача на формирование посылки       ParcelTask          AT1536DE (формат Excel)
│   ├─ В работе                         статус IN_PROGRESS (не таблица)
│   ├─ Сборка                           Assembly            SB-000001
│   ├─ Упаковка                         Packing             UP-000001
│   ├─ Взвешивание                      Weighing            VZ-000001
│   └─ Посылка                          Parcel              PS-000001
│       ├─ Комплектация коробов         Box                 KR-000001
│       ├─ Реестр отправки              Manifest            RO-000001
│       │   └─ Документы AWB            Awb                 AW-000001
│       │       ├─ Счёт на оплату услуг         AgentInvoice   SA-000001
│       │       │   └─ Заявка на выплату агенту AgentPayout    VA-000001
│       │       └─ Счёт на оплату услуг         AgentInvoice   SA-000002
│       │           └─ Заявка на выплату агенту AgentPayout    VA-000002
│       ├─ Заявка на пополнение баланса клиента TopUpRequest   PB-000001
│       │   └─ Приход ДС                        Payment        PD-000001
│       │       └─ Распределение оплат по посылкам PaymentAllocation RP-000001
│       └─ Изменение долга клиента              ClientLedger   DK-000001
```

Справочники и служебные таблицы: `StorageCell` (ячейки хранения), `Agent` (агенты / подрядчики), `DocumentCounter` (счётчики номеров).
Без изменений остались: `User`, `Customer` (клиенты и получатели), `Product` (в интерфейсе — «Услуги»).

## 3. Правила предметной области (решения владельца)

- **Одна коробка от продавца = один заказ.** Под одним входящим треком может быть несколько заказов (несколько коробок).
- **Много заказов → одна посылка.** Заказ не делится на несколько посылок.
- **Заказы попадают в посылку через задачу.** Задача собирает заказы; этапы сборки, упаковки и взвешивания — отдельные документы; по итогу создаётся посылка.
- **Каждый этап склада — отдельный документ** со своими данными (сортировка, приём, раскладка, сборка, упаковка, взвешивание). «В работе» — только статус задачи.
- **Номер документа = порядковый номер строки с префиксом** (`PS-000001`). Исключение — задача: формат Excel.
- **Трек-номер посылки** (международный: `LC…MG`, `EV…CN`, `00340…`) — в посылке. **Входящий трек-номер** (китайские службы: `SF…`, `JT…`) — в заказе. Оба не путать с номером документа.
- **Приписки к номеру из Excel** (`01 DHL`, `Sea`) — пока в примечании задачи; отдельное поле «способ доставки» решим позже.

## 4. Таблицы и поля

Общие поля всех документов: `id`, `number` (уникальный), `note`, `createdById` → `User` (сотрудник, оформивший документ), `createdAt`, `updatedAt`, `deletedAt` (мягкое удаление). Отдельная история этапов не ведётся: кто и когда выполнил этап, видно по самому документу.

### Склад

| Таблица | Документ | Поля | Связи |
|---|---|---|---|
| `Order` | Заказ | `status` (OrderStatus), `customerId`, `incomingTrackNumber` — входящий трек-номер, `description` | `parcelTaskId` → задача; 1:1 сортировка и приём |
| `Sorting` | Сортировка | `incomingTrackNumber`, `customerId?` (определённый клиент), `clientIdentified` | `orderId?` `@unique`: сортировка может быть без заказа, если коробку не опознали |
| `Receiving` | Приём заказа | `placesCount`, `weightKg`, `condition` (INTACT / DAMAGED), `photoUrl` | `orderId` `@unique` |
| `Placement` | Раскладка | — | `receivingId` `@unique`, `cellId` → `StorageCell` |
| `ParcelTask` | Задача на формирование посылки | `status` (ParcelTaskStatus), `customerId`, `destinationCountry` (ISO-2) | заказы — `Order.parcelTaskId`; 1:1 сборка, упаковка, взвешивание, посылка |
| `Assembly` | Сборка | `allFound` | `parcelTaskId` `@unique`; строки `AssemblyItem` (заказ + `found`) |
| `Packing` | Упаковка | `packagingType`, `placesCount` | `parcelTaskId` `@unique` |
| `Weighing` | Взвешивание | `weightKg`, `lengthCm`, `widthCm`, `heightCm`, `volumetricWeightKg` | `parcelTaskId` `@unique` |

### Посылка (бывший `Order`)

`Parcel` сохранил все поля из Excel: суммы в USD/CNY, курс, скидка, оплата, вес, получатель, `routePrefix` / `routeNumber` / `routeCountry` и т. д.

| Поле | Смысл |
|---|---|
| `number` | номер документа `PS-…` |
| `parcelNumber` | **трек-номер посылки** (международный). Имя поля историческое, в интерфейсе «Трек-номер посылки» |
| `parcelTaskId` | задача (`@unique`); у старых записей — задача, созданная из номера Excel |
| `boxId` | короб |
| `notes` | заметки; сюда попадает «Прежний номер» / «Номер в Excel», если номер не разобрался как номер задачи |

Связанные таблицы: `ParcelItem` (услуги и позиции, бывший `OrderItem`), `ParcelStatusHistory` (история статусов, бывший `OrderStatusHistory`), статусы `ParcelStatus` (прежние статусы заказа).

### Отправка и расходы

| Таблица | Документ | Поля | Связи |
|---|---|---|---|
| `Box` | Комплектация коробов | `weightKg` | `manifestId?`; посылки — `Parcel.boxId` |
| `Manifest` | Реестр отправки | `shipDate`, `destinationCountry` | коробы, AWB |
| `Awb` | Документы AWB | `awbNumber` (номер у перевозчика), `carrier`, `flightNumber`, `departureDate` | `manifestId`; у реестра может быть несколько AWB |
| `AgentInvoice` | Счёт на оплату услуг (входящий от агента) | `externalNumber`, `invoiceDate`, `amount`, `currency` | `agentId` → `Agent`, `awbId`; счетов на AWB сколько угодно |
| `AgentPayout` | Заявка на выплату агенту | `amount`, `currency`, `status` (PENDING / PAID / CANCELED), `paidAt` | `agentInvoiceId`; несколько заявок на счёт = частичная оплата |

### Деньги клиента

| Таблица | Документ | Поля | Связи |
|---|---|---|---|
| `TopUpRequest` | Заявка на пополнение баланса | `amount`, `currency`, `status` | `customerId` |
| `Payment` | Приход ДС | `amount`, `currency`, `method`, `receivedAt` | `customerId`, `topUpRequestId?` |
| `PaymentAllocation` | Распределение оплат по посылкам | — | `paymentId`; строки `PaymentAllocationItem` (посылка + сумма) |
| `ClientLedger` | Изменение долга клиента | `amount` со знаком (+ долг вырос, − уменьшился), `currency`, `reason` (PARCEL_CHARGE / PAYMENT / ADJUSTMENT) | `customerId`, `parcelId?`, `paymentAllocationId?`. Долг клиента = сумма строк |

Валюты (`Currency`): `CNY` (по умолчанию), `USD`.

### Статусы

- `OrderStatus`: NEW, SORTED, RECEIVED, PLACED, IN_TASK, IN_PARCEL, CANCELED.
- `ParcelTaskStatus`: NEW, IN_PROGRESS («В работе»), ASSEMBLED, PACKED, WEIGHED, COMPLETED, CANCELED.
- `ParcelStatus`: NEW, PROCESSING, PAID, SHIPPED, COMPLETED, CANCELED, RETURNED_PAID, RETURNED_UNPAID.

Задумано, что статусы заказа и задачи меняются автоматически при создании документа этапа. Эта логика ещё не написана — появится вместе с экранами документов.

## 5. Нумерация

Код: `lib/document-numbers.ts`. Счётчики: таблица `DocumentCounter` (`prefix` — ключ, `lastValue`).

**Обычные документы.** `nextDocumentNumber(tx, type)` атомарно увеличивает счётчик (`upsert` + `increment`) и возвращает `ПРЕФИКС-000001` (6 цифр). Вызывать в той же транзакции, где создаётся документ. Префиксы (`DOCUMENT_PREFIXES`) — латиница по первым буквам русского названия: ZK, SR, PR, RS, SB, UP, VZ, PS, KR, RO, AW, SA, VA, PB, PD, RP, DK.

**Задача на формирование посылки.** Формат Excel: код клиента + порядковый номер + страна, `AT1536DE`.
- `nextParcelTaskNumber(tx, customerCode, country)` — счётчик `PARCEL_TASK`, общий для всех клиентов, 4 цифры с ведущими нулями.
- `raiseParcelTaskCounter(tx, n)` поднимает счётчик до максимального номера из Excel, чтобы новые задачи продолжали нумерацию.
- `parseLegacyParcelTaskNumber(raw)` разбирает строку Excel: `/^([A-Za-z]+)(\d+)([A-Za-z]{2})(?![A-Za-z])(.*)$/` → код, число, страна, приписка. `ORD-2024003` и произвольный текст не разбираются (`null`).
- Номер собирается при создании и не меняется. Нужен код клиента (`Customer.code` пока необязателен — открытый вопрос).

**Посылки из админки.** `createParcel` (`actions/parcels.ts`) выдаёт `PS-…` в транзакции. Раньше было `ORD-<2024000+count>`.

## 6. Перенос данных из Excel

**Импорт** — `npm run db:seed` (`prisma/seed.ts`). Читает `Downloads/book-2-import.json` (результат `prisma/extract-book-2.ps1`). Поле JSON `orders` и тип `BookOrder` описывают строки Excel и не переименованы.
1. Очищает все документы, посылки, клиентов, услуги и счётчики (агенты и ячейки остаются).
2. Для каждой строки создаёт завершённую задачу из номера Excel (`prisma/legacy-tasks.ts` → `createLegacyParcelTask`) и посылку `PS-…` со ссылкой на задачу.
3. Если номер совпал с уже использованным, задача получает `-2`, `-3`… Если есть приписка или суффикс — в `ParcelTask.note`: «Номер в Excel: AT1536DE 01 DHL».
4. Если номер не разобрался — задачи нет, в `Parcel.notes`: «Номер в Excel: …».
5. Счётчик `PARCEL_TASK` поднимается до максимального номера.

**Колонка Excel «Номер посылки»** (S) → `Parcel.parcelNumber`. В ней встречаются и международные треки, и треки китайских служб (SF, J&T) — открытый вопрос.

## 7. Обновление существующей базы

Порядок обязателен:

```bash
npm run db:upgrade:001   # SQL: Order→Parcel, OrderItem→ParcelItem, OrderStatusHistory→ParcelStatusHistory, orderId→parcelId; старые индексы Order_* удаляются
npm run db:push          # создаёт новые таблицы и индексы
npm run db:upgrade:002   # TS: посылки → PS-…, номера Excel → завершённые задачи, счётчики
```

- `001` (`prisma/upgrades/001-order-to-parcel.sql`) переименовывает таблицы, а не пересоздаёт их. Сначала идут переименования, поэтому повторный запуск падает на первом же операторе и ничего не меняет. Индексы удаляются, потому что их имена (`Order_status_idx` и др.) совпали бы с индексами новой таблицы `Order`.
- `db:push` без `001` останавливается сам: Prisma не может добавить обязательное `createdById` в таблицу `Order` с данными.
- `002` (`prisma/upgrades/002-parcel-and-task-numbers.ts`) работает в одной транзакции. Обрабатывает посылки без задачи и с номером не вида `PS-`, в порядке `sourceRow` (затем `createdAt`). Задачи создаются от имени первого администратора. Повторный запуск ничего не меняет. Неразобранный номер → `Parcel.notes`: «Прежний номер: …».
- Переименование `sellerTrackNumber` → `incomingTrackNumber` (`Order`, `Sorting`) применяется обычным `db:push`: таблицы пустые, интерфейса для них нет.

Миграций Prisma (`prisma/migrations`) в проекте нет, используется `db push`.

## 8. Что изменилось в интерфейсе

- Раздел «Заказы» → «Посылки», маршруты `/orders` → `/parcels`, экспорт `/api/export/orders` → `/api/export/parcels`. Маршрут `/orders` сейчас отдаёт 404 — он освобождён под будущий раздел заказов.
- Список посылок: колонки «Номер» (`PS-…`), «Задача» (`AT1536DE`), «Трек-номер посылки». Поиск включает номер задачи.
- Карточка посылки: «Номер», «Задача», «Примечание задачи», «Трек-номер посылки».
- CSV: «Номер посылки», «Номер задачи», «Трек-номер посылки».
- Обзор и карточка клиента считают посылки.

## 10. Проверено

- `tsc`, `eslint`, `next build` проходят.
- `001` + `db:push` + `002` на базе со старой структурой: данные посылок, позиций и истории сохраняются; разные виды номеров (`AT1536DE 01 DHL`, `GG1542UA Sea`, `OS4057PL`, `ORD-…`, текст) разбираются как описано; повторные запуски безопасны.
- Сид дважды подряд на базе с документами.
- Полная цепочка документов от заказа до изменения долга создаётся и связывается.
- В браузере: список, карточка, создание посылки (`PS-…`), карточка клиента, экспорт.

## 11. Известные проблемы

- **Поиск в списках «Посылки», «Получатели», «Услуги» падает с 500** на SQLite: в запросах `mode: "insensitive"`, который SQLite не поддерживает. Было до этих изменений, не исправлено (ждёт решения владельца; при переходе на PostgreSQL заработает).

## 12. Открытые вопросы

1. Все заказы в одной посылке — одного клиента? Сейчас задача и посылка привязаны к одному клиенту.
2. Сортировка: что именно сортируют, бывает ли она до появления заказа? Сейчас допускается сортировка без заказа.
3. Два «Счёта на оплату услуг» под AWB — от каких агентов? Сейчас счетов сколько угодно.
4. Один реестр всегда = одна AWB? Сейчас у реестра может быть несколько AWB.
5. Когда меняется долг клиента — автоматически (взвешивание / посылка, распределение оплаты) или вручную?
6. Приписки `01 DHL`, `Sea`: что значит `01`, нужно ли поле «способ доставки»? Если `01`/`02` — части одной отправки, у задачи может быть несколько посылок (сейчас 1:1, дубли получают `-2`).
7. Треки SF / J&T в старых записях лежат в «Трек-номер посылки» — переносить ли их?
8. Делать ли код клиента обязательным для создания задачи?
